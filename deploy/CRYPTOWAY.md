# Cryptoway: оплата карт в USDT

## Расчёты

- Пополнение карты: сумма на карту × (1 + `CRYPTOWAY_TOPUP_MARKUP_PERCENT` / 100).
  При 3,6%: $100 → 103,60 USDT, $50 → 51,80 USDT.
- Пополнение внутреннего баланса: `balance_deposit`, 1 USDT = $1,
  без дополнительной наценки, от $1 до $10 000. Комиссия Cryptoway — расход
  ProntoPay. По прочитанному тарифу 13.11.2026 приём USDT стоит 0,5%.
  Доход возникает при расходовании баланса, а не при его пополнении.
- Выпуск: рублёвая цена из админки с реферальной скидкой / исходный индекс
  Bitbanker. Округление вверх до 0,01 USDT. Комиссии СБП и 210 ₽ отсутствуют.
- Цена и курс фиксируются в серверном расчёте, счёт действует 30 минут.
- Alipay / WeChat: CNY / `CHINA_CNY_DIVISOR`, округление до 0,01 USDT
  по обычному правилу (ROUND_HALF_UP). 2000 / 6,54 = 305,81 USDT.
  Наценка пополнения карты 3,6% здесь не применяется. В админке параметр
  называется CNY/USDT — количество юаней за 1 USDT.
- Alipay / WeChat по СБП: CNY × (индекс RUB/USDT / CNY/USDT) ×
  (1 + комиссия СБП / 100), итог вверх до рубля. Дополнительные 210 ₽
  в этом сценарии отсутствуют. Остальные сценарии СБП сохраняют свои тарифы.
- Комиссию Cryptoway платит ProntoPay. Ответ API должен содержать нулевые
  `fee_split_percent` и `markup_percent`, а `payer_amount` должен точно
  совпадать с согласованной суммой. При расхождении счёт не показывается.

## Конфигурация

Backend получает из `/opt/prontopay/backend/.env`:

```dotenv
CRYPTOWAY_API_URL=https://api.cryptoway.com
CRYPTOWAY_PROJECT_ID=
CRYPTOWAY_SECRET_KEY=
CRYPTOWAY_CALLBACK_KEY=
CRYPTOWAY_ENABLED=true
CRYPTOWAY_TOPUP_MARKUP_PERCENT=3.6
CRYPTOWAY_INVOICE_MINUTES=30
CRYPTOWAY_PAY_WITHOUT_KYC=true
PUBLIC_BASE_URL=https://prontopay.pro
```

Секретный ключ подписи API и callback key — разные. В git и админку они
не попадают. Первый запрос привязывает ключ к IP, поэтому его выполняют
с прод-сервера. Runtime env исключён из контекстов Docker.

Админка: «Криптооплаты» — счета и результаты операций; «Настройки → Оплата
USDT» — доступность способа и наценка. Изменение defaults не перекрывает
существующее значение настройки в БД.

## Сети

Показываются только активные, невиртуальные символы USDT из API Cryptoway.
На 10.11.2026: TRC20, ERC20, BEP20, TON, Solana, Polygon, Arbitrum.
Минимум проверяется по актуальному тарифу выбранной сети.

## Подтверждение и выполнение

Webhook: `https://prontopay.pro/api/webhooks/cryptoway`.
HMAC-SHA256 проверяется отдельным callback key; окно timestamp ±15 секунд.
Вложенные уведомления invoice и плоские deposit подписаны по-разному.
Webhook доступен во время техработ.

Статус callback не считается доказательством оплаты. Backend перечитывает
счёт и депозиты через API, сверяет владельца заказа, валюту, сеть и сумму.
Только `executed` и полностью подтверждённая сумма запускают услугу.
Недоплата, AML-блокировка и деньги на просроченном счёте не запускают выпуск.
Переплата видна пользователю и требует возврата разницы через поддержку.

Счета и привязка к заказам сохраняются в `cryptoway_payments`. Создание
счёта и запуск услуги предваряются сохранённой в БД блокировкой состояния.
Повторный callback не запускает второй выпуск или перевод. После таймаута
создания счёт ищется по `external_id`; POST автоматически не повторяется.
Неопределённый ответ провайдера карты передаётся на ручную проверку.
Окончательный отказ по связанному заказу возвращает оплаченную сумму на
внутренний USD-баланс ровно один раз. Неизвестный результат не возвращается
автоматически, поскольку операция могла фактически пройти.

Опрос раз в 30 секунд восстанавливает обработку после пропущенных webhook
и перезапуска. Платные операции выполняют существующие сервисы карт.

Ручная кнопка «Проверить оплату» вызывает
`POST /crypto/payments/{id}/refresh`: проверяет владельца и запрашивает
провайдера без 10-секундного ограничения фонового опроса. Уже подтверждённая
оплата возвращается из сохранённого состояния сразу. При недоступности
провайдера ручной запрос возвращает 502 с понятным сообщением; фоновые
запросы по-прежнему сохраняют состояние для следующей попытки.
В интерфейсе видны ход проверки и результат; параллельные ручные проверки
блокируются, а предыдущий фоновый запрос завершается до ручного, чтобы
старый ответ не заменил подтверждённую оплату. Это не создаёт новый счёт
и не повторяет уже выполненное пополнение.

## KYC

Pay (Rocketpay): выпуск и пополнение через Cryptoway доступны без KYC
пользователя при `CRYPTOWAY_PAY_WITHOUT_KYC=true`. Rocketpay использует
пул собственных проверенных держателей; паспорт пользователя не передаётся.
Расчёт и счёт возвращают `kyc_required=false`, интерфейс явно сообщает об этом.
С внутреннего баланса Pay также оплачивается без NeuroVision.

Online: приложение не требует NeuroVision при оплате USDT и с внутреннего
баланса. Для этих способов используется существующий отдельный сценарий
идентификации клиента O-Plata. Перед оплатой нужны действующие email и телефон.
Существующая реальная сессия, её статус и паспортные поля не заменяются:
при pending/failed данные для O-Plata передаются через отдельное представление.
Это не отменяет собственные проверки и ограничения карточного провайдера.
`PUT /crypto/contact` сохраняет только контакты; не меняет KYC и паспорт.
Сохранение контактов доступно и при отключённой криптооплате.

Все назначения СБП — выпуск, пополнение карты, внутреннего баланса,
Alipay/WeChat — требуют успешного реального NeuroVision до запросов к шлюзу.
Синтетические данные этот доступ не открывают. Прежние лимиты СБП сохраняются.
Универсальные legacy-типы O-Plata не получают исключение обычной Online.

Зачисление крипты на внутренний баланс и `fulfillment_status=completed`
фиксируются одной транзакцией под блокировкой строки платежа. Повторные
callback и опросы не зачисляют деньги повторно; прерванная транзакция
откатывает и зачисление, и статус. В истории записывается `crypto_deposit`
с номером криптосчёта. Отдельный заказ карты не создаётся.

## Заявки Alipay / WeChat

Способ оплаты фиксируется при создании заявки и не меняется задним числом.
Дополнительно доступен `balance`: цена CNY / `CHINA_CNY_DIVISOR` в USD,
без комиссии СБП и без зависимости от рублёвого курса. Фиксируется в
`amount_usdt` как эквивалент USD и возвращается интерфейсу как `amount_usd`.
`POST /services/requests/{id}/pay-balance` проверяет владельца, срок и статус,
блокирует заявку и атомарно списывает баланс вместе с переводом в `paid`.
Повторная оплата не списывает деньги и не передаёт менеджерам вторую заявку.
Крипто- и СБП-callback не могут оплатить заявку с методом `balance`.
Криптозаявки сохраняют `amount_usdt` и `cny_per_usdt`; криптосчёт с назначением
`china_payment` ссылается на принадлежащий пользователю `service_request_id`.
До создания внешнего счёта родительская заявка блокируется и проверяется,
чтобы по ней не было другого активного / оплаченного / спорного счёта.
СБП не принимает криптозаявки. Оплата USDT не зависит от доступности СБП
или API рублёвого курса и не требует KYC карты.

Только подтверждённая полная оплата переводит заявку в `paid`, записывает
`crypto_payment_id` и передаёт её менеджерам существующим механизмом.
`fulfillment_status=completed` здесь означает принятую оплаченную заявку;
фактический перевод юаней менеджер завершает статусом `done`.
Повторные уведомления не создают заказ карты и не отправляют вторую заявку.
Заявки с криптосчетами сохраняются для аудита, удаление в админке запрещено.
Новые поля добавляются при старте backend; старые заявки остаются СБП,
с прежними фиксированными суммами.

Контрольный клиент
`pp_crypto_probe_20261110` создан без паспорта: регистрация успешна, но
проверка выпуска Online вернула `IDENTIFICATION_DOCUMENT_ABSENT`.
Этот результат не подтверждает поддерживаемый выпуск без паспортных данных.
Это историческая проверка пустого профиля провайдера, а не реальный платный
тест текущего сценария идентификации. Выпуск новой карты и приём реального
USDT-перевода в проверках этого изменения не выполнялись.

## Проверка

Из `backend`: `venv/Scripts/python.exe -m unittest discover -s tests -v`.
Frontend: `npm run build`.
Проверять реальные счета следует с сервера, без повторения POST при таймауте.
Создание и отмена неоплаченного счёта не проверяют on-chain зачисление:
для полного боевого теста нужен отдельный перевод и подтверждение сети.
