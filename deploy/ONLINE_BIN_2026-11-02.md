# Online: переход на новый сингапурский тип карты

Изменения подготовлены локально 02.11.2026. На прод не применялись.

## Проверка API

Выполнен только запрос чтения `POST /product/rest/card/virtual/list`
для существующего клиента `PRONTOPAY` через сервер приложения.
Регистрация клиентов, выпуск, переводы, изменение настроек и уведомления
не выполнялись. Процесс приложения не перезапускался.

У актуального типа:

- `paymentSystem=MASTERCARD`, валюта карты USD, баланс провайдера USDT.
- `transactionConstantFee=0.8`, `transactionPercentFee=0`.
- `transactionMaximumAmount=10000`, `validityPeriod=24` месяца.
- У провайдера `issueConstantFee=3` USDT, `minimumCardBalance=1`,
  `maxIssuedCount=10`. Это параметры провайдера, не розничная цена.
- Описание исключает Apple Pay/Google Pay, игровые сервисы и Meta.

Страну **Сингапур** подтвердил Александр в последнем сообщении пользователя.
Сам `cardTypesList` не содержит страну или цифры BIN. Цифры нового BIN
без выпуска карты этим запросом не подтверждены. Реальную карту не выпускали.

API также возвращает доступные VISA RT-2
(`9535aec3-3c6a-4130-b9c2-27d887e54041`) и RT-11
(`bdd11ad8-ebc2-4603-8a6b-1acab9ccd13f`). Они не относятся к запрошенной
замене Online и по-прежнему скрыты в приложении. RT-8 типов для выпуска не вернул.

## Подготовленные изменения

1. Текущая Online — `RAVANA:RT-prod:f5d8ea65-6c55-43e6-b7a1-19e103be42ce`.
2. Старые три UUID перенаправляются прямо на новый при выпуске,
   включая обработку ранее оплаченных СБП-инвойсов и recovery.
   Старые типы не продаются повторно даже при изменении `readOnly` провайдером.
3. Новые локальные строки Online получают сингапурское имя и адрес HDB
   с шестизначным индексом соответствующего дома. Сохранённые данные
   существующих карт не перегенерируются; Pay остаётся HK.
4. Значения по умолчанию backend и frontend: Сингапур, $0.80, 2 года.
   FAQ по умолчанию и лимит Online на лендинге приведены к $10 000;
   убраны неподтверждённые утверждения об одинаковой комиссии отказа
   и общем лимите $2 млн.
5. Подготовлен `backend/migrations/switch_online_sg_20261102.sql`:
   страна, операция, срок и точечное исправление FAQ. Применение повторяемо.
   SQL не изменяет карты, кошельки, заказы или платежи.

Текущие значения прочитаны из прод-БД: Online включена, цена 1499 RUB,
наценка пополнения 3.6%, страна «🇭🇰 Гонконг», операция 0.55.
Цена выпуска, наценка пополнения и Pay в этом изменении не меняются.
Настройки из БД перекрывают defaults: один деплой кода не обновит витрину.

## Проверки

- `backend/venv/Scripts/python.exe -m unittest discover -s tests -v`
  из `backend`: выбор актуального типа, скрытие retired/readOnly,
  перенаправление старых оплаченных offer_id до вызовов провайдера,
  SG-адрес/индекс, HK для Pay, сохранение существующих данных.
- `npm run build`.
- Разбор Python AST и `git diff --check`.
- Сопоставление локальных offers с сохранённым реальным ответом API
  выполняется с подменой сетевых вызовов и отключённой отправкой уведомлений.

Результат: все 8 тестов прошли; на реальном сохранённом ответе локальный
каталог предлагает ровно один тип O-Plata — новую Online. Сборка завершена
успешно, Python AST и `git diff --check` без ошибок. В сборке остаётся
предупреждение исходного `index.html`: блок `noscript` Метрики расположен
в `head`; файл в рамках этого переключения не менялся.
SQL подготовлен, но на базе не выполнялся. Реальный выпуск не тестировался.

## Применение после отдельной команды пользователя

1. Проверить отсутствие незавершённых операций и состояние рабочей копии
   сервера; сохранить текущие значения трёх настроек и затрагиваемого FAQ.
2. Доставить проверенные изменения и SQL, сверить SHA и результат pull.
3. Применить SQL к целевой БД и пересобрать backend/frontend согласованным
   релизом. Backend загружает значения из БД при старте.
4. Проверить `/auth/config`, `/cards/offers`, админский список типов,
   витрину Online и неизменность Pay. Если нужен реальный тест выпуска —
   отдельно согласовать его, поскольку он расходует деньги.

До команды пользователя эти шаги не выполняются.
